## Recommended execution order

**002 → 001 → 003.** Reasoning:

- 001, 002, and 003 all introduce the same `--ease-out` token into `demo/styles.css`'s `:root` block. Each plan is written to be self-contained (checks whether the token already exists before adding it), so they can technically run in any order or independently — but running **002 first** means 001 and 003 will find the token already present and can skip that sub-step cleanly.
- 001 and 002 are both CSS-only, low-risk, and touch non-overlapping selectors (`.ring-node`/`popNode` vs. `.tab-btn`/`.btn`/`.node-circle`) — no conflict between them regardless of order.
- 003 is the highest-risk plan (touches JS across 2 files at ~13 call sites, not just CSS) — run it last, after the two simpler plans have proven the `--ease-out` token and local dev workflow are working.

## Dependencies between plans

- **003 depends on the `--ease-out` token existing** (from 001 or 002, or added by 003 itself if run standalone — its own Steps section handles this).
- **003 does not depend on 001 or 002's actual rule changes** — it touches entirely different CSS rules (`.modal-overlay`/`.modal-window` vs. `.ring-node`/`.tab-btn`/`.btn`/`.node-circle`) and a different file (`demo/app.js`, which 001/002 never touch). It only shares the token.
- No plan depends on another plan's JS changes — only 003 touches JS, and it's self-contained.
